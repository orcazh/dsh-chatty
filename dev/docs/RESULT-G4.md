## 实机现象

用户点的「真发一次」，目标会话就是拟人化输出生效的那个会话。截图记录：

```
┌──────────────────────────────────────────────┐
│ [图标] 收到执行请求                     20:55 ⌄ │   ← 灰底、可折叠
└──────────────────────────────────────────────┘

已完成，用时 5 秒 ⌄                                  ← 回合状态行

这念头不是本鱼自己冒出来的，是你塞进来的。            ← 第 1 条气泡
而且是「主动打招呼」就得真去发消息，这属于动手操作……   ← 第 2 条
真想让我给谁发 QQ，就说清楚发给谁、发什么，本鱼照办。  ← 第 3 条
```

| 观察项 | 结果 |
| :--- | :--- |
| 触发消息的实际样式 | 灰底、带图标、可折叠的一行「收到执行请求」+ 时间戳 |
| 是否出现用户气泡 | **否**（没有右侧气泡，没有头像）✅ |
| 是否触发真实 LLM 请求 | 是（有思考过程，用时 5 秒，真花了 token）✅ |
| 回复是否走多条气泡 | 是，3 条，且**外观与正常回合完全一致** ✅ |
| 回合状态行 | 「已完成，用时 5 秒」正常出现 |

**关键结论**：followup 产生的回合走的是和用户提问**完全同一条渲染路径**。
我们的气泡视图不需要为 followup 做任何特判 —— 它看到的就是一个普通的
assistant step。

## API 契约（照 `dsh-speak-up` 的实现抄准）

### 取活着的 agent

```js
ctx.agents.get(id)      // 不是 sessions.scope(id)
```

两种 id 写法都要试（`xxx` / `session-xxx`），顺序：原样 → 补前缀 → 去前缀。

### 前置条件（三条，缺一不发）

| 条件 | 判据 | 理由 |
| :--- | :--- | :--- |
| agent 活着 | `ctx.agents.get(id) !== undefined` | 冷会话需要先唤醒 |
| 不忙 | `agent.status === 'idle'` | 正在跑 Turn 时插话会打架 |
| 未归档 | 不在 `workspaceRegistry.archivedSessionIds` | 归档 = 废纸篓 |

`dsh-speak-up` 的选择是**不自动唤醒**冷会话（「按设计不自动唤醒，这轮什么都不做」）。
我们把这条沿用为默认策略：宁可不补，也不要莫名其妙拉起一个后台 agent。

### 消息形状

首选 `import('@deepseek-ai/dsh-llm')` 的 `createUserMessage({ content, source })`；
拿不到就手搓（形状是照它抄的，`dsh-session` 的校验只需满足这几条）：

```js
{
  id: 非空字符串,
  role: 'user',                          // 只能是 user，见下
  content: [{ type: 'text', text: '…' }],
  source: { kind: '…' },                 // 非空字符串
}
```

### 两个必须遵守的坑

**① `await` 不能省。**

```js
await agent.followup(消息)
```

不 await 的话，它 reject（会话忙 / agent 已释放 / 流出错）就是未处理的
rejection；Node 22+ 默认把它当致命错误 —— **整个 DSH 宿主进程退出**。
（speak-up 的作者 2026-10-21 真的收到过「装了鱼就死了」的反馈。）

**② 角色只能是 `user`，这不是选择。**

`dsh-agent-loop` 在 `step()` 里把收件箱认领到的消息**硬写成** `user/message`
事件，不看 `message.role`。所以在模型眼里，这条 followup **就是用户说的话**。

截图里模型回「这念头不是本鱼自己冒出来的，是你塞进来的」就是证据。
`dsh-speak-up` 为此专门做了一层「框住内心话」的包装（2026-10-24 修），
否则模型会把触发文案当成用户在跟它说这句话，顺着回答。

**这条对我们的直接影响**：FR-5 补句的文案必须写成
「（承接上文，补一句你自己想说的话）」这种**可被识别的插入标记**，
不能写成像用户指令的祈使句，否则模型会去「执行」而不是「接着说」。

## 尚未实测、但已在设计上兜住的两项

| 项目 | 计划中的处理 |
| :--- | :--- |
| 补句期间用户又发消息 | 只在 `agent.status === 'idle'` 时才发；发送后不做任何重试 |
| 关闭插件后定时器 | FR-6 的定时器一律挂 `ctx.effect` 的清理，插件卸载即停；不做「内存里自己 setInterval」那套 |
| 冷会话 | 默认不唤醒（同上），设置页给出的会话都是侧栏里现存的 |

---

## 判定

计划里的标准是「样式可接受 + 生命周期可控」：

- **样式可接受** ✅ 灰底一行、可折叠、不出用户气泡，回复外观与正常回合一致
- **生命周期可控** ✅ 有三个明确的状态闸门（活着 / 不忙 / 未归档），
  且 speak-up 在同一台机器上长期运行，说明这套闸门在实践中站得住

→ FR-5 / FR-6 **按原需求做**，不降级、不砍掉。
