# 「取消勾选之后还在生效」：查到了什么，改了什么

**日期**：2026-10-28
**结论**：**取消勾选确实能取消掉，但旧页面的取消动作有一大半没落盘。**
另外「模型自检说规则还在上下文里」是**真的**，而且和配置无关 —— 那是历史。

---

## 一、先看事实

用户报：「昨天在设置里取消了勾选，之后回复仍是分段风格。让模型自查，它说注入的
回复要求还在上下文里。」

逐条查证（都在本机，可复现）：

| 证据 | 内容 |
| :--- | :--- |
| `~/.dsh/chatty/config.json` | `mode: "allowlist"`，白名单**包含** `session-351816c0-…` |
| 该文件 mtime | `2026-10-27T13:14:27Z` —— 之后再没有任何一次写入 |
| `~/.dsh/chatty/logs/sessions.jsonl` | 该会话最近一次记录 `enabled: true` |
| 会话日志（`~/.dsh/sessions/…/session.v4.jsonl.zstd`，解压后 443 行） | `system/message` 共 4 条，出现在 turn 1 / 2 / 11 / 17；turn 2 / 11 / 17 的提示词里**确实含有**「【回复分段规范】」 |

也就是说：

1. **配置里那个会话一直是勾上的**。模型说「白名单只放行两个会话，按理不该进当前
   会话」——它看错了，第二个 id 就是当前会话。
2. 用户以为的「取消勾选」**没有写进文件**。旧页面的勾选框只改页面里的本地状态，
   要点一次「保存」才落盘；文件 mtime 停在 21:14（本地），之后一次写入都没有。

所以第一层原因不是「过滤没生效」，而是**取消动作根本没送到宿主**。`isEnabled()`
本身是 fail-closed 的（白名单里没有就是 `""`），smoke 一直在覆盖这条。

---

## 二、第二层原因：历史里真的有旧规则

`system/message` 只在提示词**变化**时才追加一条完整提示词（19 个回合里只有 4 条）。
我们这条 section 的正文会写进其中。取消勾选后，下一回合组装出来的提示词里没有它了，
但**之前那几条已经进了会话历史的 `system/message` 不会消失** —— 模型翻上下文
仍然能看到旧规则。它说「上下文里还保留了被注入的回复要求」，这句是准确的。

再加上第三层：**风格惯性**。前面十几条回复全是短段，模型会照着学。即使规则彻底
撤掉，它也会再维持一两轮短段。这和「规则还在」是两件事，但对人的观感一样。

**这三层都改不掉历史，只能改未来**：规则不再注入（已验证）、新回合开始就换掉
旧提示词（DSH 行为）、风格惯性靠新会话最快。觉得「怎么还没变回去」时，
**开一个新会话**是最快的判定方式。

---

## 三、改了什么

| 改动 | 为什么 |
| :--- | :--- |
| 去掉「在选定会话当中生效」开关，`mode` 由列表推导（空 = `off`） | 开关和勾选状态可能互相矛盾，正是「到底关没关」的来源 |
| 去掉「保存」按钮，所有控件自动保存（300ms 防抖） | 取消勾选立刻落盘，堵死「忘了点保存」这条路 |
| 列表前加「全选」（三态：全选 / 半选 / 全不选） | 用户提的交互；全不选就是彻底关闭 |
| 列表下方加实时汇总「当前：N / M 个会话生效」 | 一眼看出关没关，不用去翻配置文件 |
| 勾选里残留的、不在当前列表的 id 单独提示 | 否则会出现「看不见但生效」的会话 |
| **新增 `~/.dsh/chatty/logs/section-decisions.jsonl`** | 每次组装提示词记一行：`ts / sessionId / mode / enabled / chars`。以后再怀疑「到底注入没有」，看文件，不要问模型 |

`section-decisions.jsonl` 的读法：

```jsonl
{"ts":"…","sessionId":"session-351816c0-…","mode":"allowlist","enabled":true,"chars":312}
{"ts":"…","sessionId":"session-351816c0-…","mode":"off","enabled":false,"chars":0}
```

`enabled:false` + `chars:0` = 这一回合什么都没注入。如果取消勾选后这一行没变，
问题在客户端没保存；如果变了但仍出现分段风格，那就是历史惯性，不是规则。

---

## 四、顺带修的一个相关问题：忙碌期间连发消息

DSH 自己的行为：agent 正在跑的时候，用户再发的消息进收件箱，等这一回合结束
再开下一回合（界面上会显示成 steer 气泡）。**这不需要我们加规则**，是原生的。

但它有一个副作用落在我们这边：上一回合的气泡如果还在一条条往外冒，
新回合已经开始生成了，两边会「抢话」。现在**任何新回合一开始（`turn` 变大且
处于 `running`），所有更旧的 reveal 立刻判定为完成、整段显示**，
旧气泡不会再往新回合里冒。

---

## 五、怎么验收

1. 托盘退出 DSH → 启动（`client.js` 改了，`Ctrl+R` 无效）
2. 设置 → 拟人化输出：确认**没有**顶部开关、**没有**保存按钮，列表前有「全选」
3. 取消当前会话的勾选（页面立刻显示「已保存，立即生效」，汇总变成「当前：一个会话都没勾」）
4. 在同一会话里发消息 → 回复应当**保持 DSH 原样**（不再分段）
5. 检查 `~/.dsh/chatty/logs/section-decisions.jsonl` 最后几行：
   该会话应为 `"enabled":false,"chars":0`

> 第 4 步的预期要放宽一点：如果这个会话之前已经连着回了十几条短段，
> 模型可能还会接着写一两轮短段。这不是规则还在，是它在学自己。
> 想立刻看到差别，**开一个新会话**。
